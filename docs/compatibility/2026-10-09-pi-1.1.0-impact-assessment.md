# Pi 1.1.0 对 only-my-pi 的影响评估

评估日期：2026-10-09。范围：当前工作树与 Pi 0.85.1 → 1.1.0 的累计差异。源码基点：`8240603576088a688f2fc0bbd8c38950bd4245bc`，分支 `codex/webui-phase1`；评估包含原有未提交修改，不能将结论归给这个 commit 的干净树。

**结论：当前已安装的 OMP 不会因上游发布而自动变化；主动升级是跨模块的运行时迁移，不能直接替换版本。建议保留 0.85.1 日常栈，先建立独立的 1.1.0 迁移规格和隔离候选，在 U2–U6 大规模实现前确定目标运行基线。现有 G2 材料补齐可以继续，升级不解除它的前置条件。**

本轮完成官方版本、实际发布包和源码接点的静态评估，以及本地版本合同的只读探针。未安装或执行 Pi 1.1.0，未调用模型、读取凭据、改变运行栈、修改工单或升级依赖。动态兼容、第三方扩展组合、浏览器、Full、真实 Provider 和日常晋升均为 `NOT_RUN`。

**1. 当前合同明确拒绝 1.1.0；第三方补丁不能误认为 Pi 核心补丁。**

[piRuntimeContract](../../packages/release-stack/contracts.mjs) 的只读实测结果如下，未创建任何候选：

```text
0.84.3 -> admitted
0.85.1 -> admitted
1.1.0  -> STACK_PI_IDENTITY_INVALID: unknown controlled Pi version
```

[distribution/runtime.mjs](../../packages/distribution/runtime.mjs) 113–119 行还核对实际 Pi 版本、产物树及 Full 栈绑定；[private-runtime.mjs](../../packages/release-stack/private-runtime.mjs) 18–25 行使用 `phase1-pi0851`。因此只改根依赖声明不能通过安装身份校验。

[runtime-patches.mjs](../../packages/distribution/runtime-patches.mjs) 14–21 行约束的是版本化补丁合同和精确输入 SHA-256；其中 `version` 是 OMP 产品版本，不能误读为 Pi 版本。补丁目标是 `pi-web-access@0.25.0`、`pi-permission-modes@2.2.0` 和 Linux 的 sandbox-runtime。下载的 Pi 1.1.0 npm 包不包含这些独立外部包，所以不能据此宣称它们的补丁 anchor 已经失效或已经兼容。新候选必须对选定的外部包实物复验。

Pi 从 1.0.1 起不再随 npm 包发布 shrinkwrap。1.1.0 的实际依赖新增 `@earendil-works/pi-mcp`、`@earendil-works/pi-codemode`、`quickjs-wasi@3.6.2`、`brace-expansion@5.0.12`。即使暂不启用 MCP/codemode，发行材料范围也已扩大。应冻结实际依赖树，并更新 artifact ledger、SBOM、来源与许可材料清单；不能由本报告认定许可闭合。[上游说明](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/CHANGELOG.md#101---2026-10-03)、[发布包依赖](https://registry.npmjs.org/@earendil-works/pi-coding-agent/1.1.0)

**2. 缓存保温是本轮发现的实质接入风险。**

[上游 settings-manager.ts](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/settings-manager.ts#L1045) 1045–1049 行在没有设置时返回 `streaming`；[sdk.ts](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/sdk.ts#L333) 创建 CacheWarmer，并在会话请求后启动它。缓存 TTL、可重放性、有效价格和预期节省等条件满足时，它会再次 `streamSimple(..., maxTokens: 1)`，将费用写成 `usage` / `cache_warm` 条目，并触发 `entry_appended`。默认不是持续 idle warming，也不是每次任务都会额外请求。[cache-warmer.ts](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/cache-warmer.ts#L331)

当前 [Host tasks](../../packages/host/tasks.mjs) 128–144 行只对 assistant 的 `message_end` 调用 [recordUsage](../../packages/host/usage.mjs)，没有处理 `entry_appended` 的独立 usage。源码据此可确认该类记录没有聚合接点；本轮没有触发真实费用，也没有测得漏记金额。`allowModelNetwork: false` 限制的是模型目录刷新，不能作为禁用缓存保温的依据。

建议首个候选显式采用 `cacheWarming: off`，核实设置在 SDK 服务创建与每次会话替换后均生效。若未来启用，需先定义授权、请求预算、取消/退出、账号归属和费用聚合，并验证真实请求数与持久记录一致。该建议尚未写入用户设置。

**3. 新工具不会在当前 Host 中自动开启，但不能继续依赖旧白名单语义。**

[Host account-rpc-entry](../../packages/host/account-rpc-entry.mjs) 41–53 行、[direct TUI](../../packages/direct-agent/tui-runtime.mjs) 61–88 行及 [account child](../../packages/host/account-child.mjs) 31–43 行均显式使用 `noExtensions: true` 和受控扩展路径。[新版 loader](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/resource-loader.ts#L573) 在此模式只加载显式选择项；SDK services 直接使用调用者提供的 factory，没有自动注入本项目未提供的 builtin factories。因此不能把“上游新增内置 MCP/codemode”直接判为本项目已自动加载或存在越权。

但是 [新版 tools 合同](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/sdk.ts#L72) 明确规定：普通 `tools` allowlist 会保留 MCP 注册工具，除非匹配项以 `mcp__` 开头；空列表/`noTools: all` 的规则另列。当前 [launcher](../../packages/direct-agent/launcher.mjs) 12–17 行将 `--tools` 视为注册白名单的说明已不足以覆盖新版所有模式。

当前 [权限控制](../../extensions/omp-direct/runtime.mjs) 240–252 行限制 active tool 集合，635–653 行按工具名称检查写入。若以后启用 MCP、codemode、deferred/model-only tools 或 `ctx.executeTool()`，需要验证外层和嵌套调用均经过权限、路径、网络、取消与预算边界；上游也提供 `parentToolCallId`，不能把嵌套工具事件当成单一串行工具。[上游扩展事件类型](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/extensions/types.ts)

首轮迁移建议保持新增内置能力关闭，先验证既有 permission-modes、subagents、LSP、usage 和受控 first-party 扩展。当前 `user_bash` 返回 `{result}` / `{operations}` 的方式符合新版 fail-closed 形状；行为仍需真实扩展组合验证。[本项目事件接点](../../extensions/omp-direct/index.ts)、[上游 user_bash 变更](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/CHANGELOG.md#0860---2026-09-19)

**4. 会话体系仍可沿用，需调整和验证的是上下文语义。**

实际 1.1.0 发布包仍导出 `ModelRuntime`、`SessionManager`、`createAgentSessionServices`、`createAgentSessionFromServices`、`createAgentSessionRuntime`、`AgentSessionRuntime`、`runRpcMode`。`SessionManager.create/open/inMemory/forkFrom/list/listAll` 和 `AgentSession.sendCustomMessage({customType, content, display, details}, {triggerTurn, deliverAs})` 仍存在，与当前主要调用形状相符。[公开入口](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/index.ts)、[SessionManager](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/session-manager.ts#L1755)、[sendCustomMessage](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/agent-session.ts#L2293)

0.87 起 SessionManager 成为 provider 请求上下文的权威；只赋值 `session.agent.state.messages` 不再替代请求历史。本项目 [session-runtime.mjs](../../packages/direct-agent/session-runtime.mjs) 173–175 行在 `newSession.setup` 后仍做这种赋值。它此前已先修改 SessionManager，所以不能仅凭这一行断言历史丢失；应对照新版官方 runtime 的 `session.refreshContext()` 路径完成适配和回归。[上游对应实现](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/agent-session-runtime.ts#L253)

两版 `CURRENT_SESSION_VERSION` 均为 3，但新版增加 `context_edit`、`usage` 等条目。相同 header version 不意味着双向无损兼容。新旧候选必须使用独立会话副本，验证旧历史续接、新历史解析、fork、compaction、恢复与回滚；不得先让新 Pi 写入唯一日常历史，再假设旧 Pi 能完整理解。

新 RPC 的 `prompt/steer/follow_up` 成功响应附带 `disposition`；`steer/followUp` 返回 disposition，`AgentSession.prompt()` 则通过 `preflightResult` 回调给结果，本身仍是 `Promise<void>`。[RPC 实现](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/modes/rpc/rpc-mode.ts#L394)

这是可利用的反馈增强，不等于持久消费收据。本项目 [pi-input-bridge](../../packages/host/pi-input-bridge.mjs) 15–22、48 行仍需用 `details.inputId` 与 [input-protocol](../../packages/host/input-protocol.mjs) 的历史校验实现崩溃后核对。[ADR-0018](../decisions/ADR-0018-host-input-ledger-and-pi-correlation.md) 的意图/消费分离仍有必要。

**5. 账号和界面属于明确回归范围，部分上游 breaking change 当前没有直接接点。**

`ModelRuntime.create` 的 `authPath/modelsPath/modelsStorePath/allowModelNetwork/refreshOnCreate` 参数和 `getAvailableSnapshot()` 仍存在；chat 模型快照与新增 image/classifier 模型接口分列。[ModelRuntime 源码](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/model-runtime.ts)

1.0.3 将 Provider ID `azure-openai-responses` 改为 `azure`；上游说明旧 ID 的历史可能 fallback。本项目 [account-rpc-entry](../../packages/host/account-rpc-entry.mjs) 31–55 行绑定账号/provider/model 且拒绝 fallback，因此使用旧 Azure ID 的场景可能被正确阻断，需显式迁移与再验收。本轮没有读取 auth 文件，也不推定用户使用 Azure。[官方迁移说明](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/CHANGELOG.md#103---2026-10-05)

Pi 1.0 默认 fullscreen，而本项目 [tui-runtime](../../packages/direct-agent/tui-runtime.mjs) 109–111 行透传选项；未指定时会得到新版默认行为。可用 `--tui-mode regular` 保持普通终端 scrollback；迁移规格应明确选择，并通过真实 PTY 与 Ego Lite 内嵌终端旅程验证。[上游默认设置](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/src/core/settings-manager.ts#L1371)

对当前 `packages/`、`extensions/` 接点检索没有发现使用已删除的 `AgentHarness` / `shouldStopAfterTurn`，也没有自制 provider EventStream。会话选择器使用上游 [ProcessTerminal](../../packages/direct-agent/session-picker.mjs)，不是自行实现 Terminal；上游 ProcessTerminal 已实现新增 `setProgramStatus`。这几项 breaking change 不能作为本项目必然重写的依据；未运行的第三方扩展仍需检查。[agent-core 变更](https://github.com/earendil-works/pi/blob/v1.1.0/packages/agent/CHANGELOG.md#100---2026-10-01)、[pi-ai 变更](https://github.com/earendil-works/pi/blob/v1.1.0/packages/ai/CHANGELOG.md#110---2026-10-07)、[Terminal 实现](https://github.com/earendil-works/pi/blob/v1.1.0/packages/tui/src/terminal.ts#L576)

**建议的下一步：单独形成迁移规格，再按以下四个交付边界拆工单。**

1. **冻结与隔离候选。** 确定精确 Node/Pi/外部包组合、完整锁、artifact identity 和来源清单；新增版本化合同而不替换旧合同。明确初始工具集合、缓存保温 off 和 TUI 模式。最低完成条件是候选身份闭合与独立空配置下无模型启动，未知版本和篡改输入继续拒绝。
2. **SDK 与扩展适配。** 验证公开 API、会话 context refresh、账号/provider/model 隔离、read-only/controlled 工具边界、写入审批、子代理物理 owner、取消和 shell 策略。类型检查和局部测试只是其中一层；必须加载真实 1.1.0 与精确扩展包。以本地受控 Provider 统计实际请求，证明关闭缓存保温后没有额外模型请求；此结果与真实 Provider 分列。
3. **U0/U1 与终端回归。** 在独立会话副本运行 Host 公开入口、prompt/steer/queue、crash/reconcile、resume/fork/compaction、图片和 usage 场景；用 Ego Lite 验证页面和终端旅程。冻结即将进入 U2–U6 的运行基线与接口差异。首轮若不启用 MCP/codemode，就验证它们未加载，而非开展无关功能建设。
4. **发行和晋升。** 在相应 G2 材料、native/parser 前置满足后，生成源码绑定的隔离 Full、离线和缺失/漂移负例证据；再按 [ADR-0017](../decisions/ADR-0017-versioned-runtime-contracts-and-stack-promotion.md) 做独立日常切换、回滚和再应用。实际安装切换、真实 Provider 费用和发布仍需该目标与范围的授权。
