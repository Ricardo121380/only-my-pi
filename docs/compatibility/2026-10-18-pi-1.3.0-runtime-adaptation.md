## 2. 公开入口与产品职责

已对照取得的 1.1.0 / 1.3.0 公开类型与实现：[SDK 文档](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/sdk.md)、[RPC 文档](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/rpc.md)。`createAgentSessionServices`、会话 runtime、ModelRuntime、RpcClient/RPC 命令类型保持兼容；新增 `before_agent_start.messageType` 区分 user/custom，启动期间已算 busy，恢复时可恢复原工具集合。

| 能力 / 公开入口 | Pi 承担 | OMP 承担及本轮处理 |
| --- | --- | --- |
| `omp` → Pi `InteractiveMode` / SDK runtime；`runPrintMode`、`runRpcMode` | TUI、Agent loop、模型请求、工具执行、消息/历史与结束事件 | 继续独立 CLI，无 WebUI 前置；固定工具/扩展集合、项目及会话占用、只读/编程准入。打印路径复用既有受控 SDK 工厂，以便施加与 TUI/RPC 相同的请求政策 |
| Host HTTP / `RpcWorker` → `account-rpc-entry` → SDK | `createAgentSessionServices`、`createAgentSessionFromServices`、正式 RPC | 配对、显式账号/模型、审批、撤权、项目单写、进程身份与终止核验。保留所需的账号专属子进程，无整体 Host/worker 重写 |
| `sendCustomMessage`、`details.inputId`、持久 custom message | 在安全点排队和消费，保存历史条目 | Host 先保存意图；ACK 表示接收，消费须关联真实历史。丢 IPC/HTTP ACK 查回执，不重发；启动忙碌、取消及未知状态均分别回归 |
| `ModelRuntime.create` 与账号公开凭据 API | Provider/模型目录及认证机制 | 每任务固定产品账号、Provider、模型；无自动账号回退，执行前重新检查凭据；分类/生图仍按原绑定、逐调用许可、预算及账本工作 |
| SDK 内置能力的显式装配 | `McpClient` / OAuth、`createToolSearchExtension`、`createCodemodeExtension`、QuickJS 与模型 API | `installOmpMcp` 使用 OMP 的准入配置和原生 client，显式安装受控搜索/资源辅助能力；`installOmpCodemode` 显式装配原生 codemode 与分类/生图。CLI 传 `--no-mcp` 禁止上游环境自动发现 |
| 缓存保温与请求重试 | Pi 提供公开 warming hook、SettingsManager 读取接口 | `disableOmpCacheWarming` 最后装配；`applyOmpRequestPolicy` 在本会话的公开设置读取处固定 Agent/Provider 两层重试为零，跨资源重载和 RPC retry toggle 生效，不修改 raw Pi 文件来施加政策 |

上游 `RpcClient` 可承担一般命令关联和事件分发，但当前版本固定 `spawn("node")`、合并环境、转发原始 stderr，仅管理直接子进程；没有本项目的 Node 绝对路径、账号 IPC、`omp_input_*`、受控审批代次和项目/进程组终止证明。因此本票保留 `RpcWorker`；删除它需要另有相同行为证据，不能仅以封装更短替代本票验收。

`packages/upstream-compatibility/native-pi.mjs` 显式保留原 native `1.1.0` 并新增 `1.3.0`，历史 `0.84.3` / `0.85.1` 保持原工具路径。CLI、codemode、MCP 和 Host 的 codemode 审批桥共用这一有界判断；MCP/codemode 包名必须正确，版本必须与 Pi 完全相等。实际公开 CLI 对未准入的 `1.3.1`、缺失或损坏 manifest、缺失 version、错误包名，均在模型请求前拒绝。版本身份不明不能降为历史模式；单元测试的旧运行栈明确声明其合成 `0.85.1` 身份。

打印接入调整的行为依据包括实际公开 CLI：保留持久/内存会话、JSON/text、显式模型、只读工具、已占用历史拒绝、文件与 stdin 拼接、多条提示顺序、退出码、取消及终端恢复。JSON/RPC 的进程正常结束不等于模型成功；模型失败仍核对 `stopReason:error`、`willRetry:false` 与独立接收数。
