# G2-N04：让默认发行包完整携带 parser 资源与元数据

状态：OPEN；分流标签：ready-for-agent。执行前核对全部前置和操作条件。

## Parent

[总规格 #19](https://github.com/Ricardo121380/only-my-pi/issues/19)，原 Task G2-00-05，需求 US-014，并遵守 US-001–US-004。出口为 F03 默认接线与 F04 最终内容/元数据；公开软件发行另有授权边界。

## What to build

维护者使用正常的受控发行准备与组装入口，就能从已验收的 parser 候选得到完整 app 包及对应获取台账、两种 SBOM 和 notices。无需手工注入、复制开发目录或依赖演练用途；丢失资源、声明或身份不一致时，正常流程明确失败。

## Acceptance criteria

以下为 2026-10-10 总规格扩展的追加条件，原条件继续有效。

- [ ] 默认 acquisition/staging/assembly 将经 PI110-N04 核验的 Pi 1.1.0、MCP/codemode 及真实必需资源，与 parser 资源共同纳入最终内容、ledger、双 SBOM/notices，保留各自身份。
- [ ] 历史受控补丁只按新合同的真实版本/摘要/锚点使用；不得为了构建通过接受旧 runtimeContract 或无来源目录。

- [ ] 默认发行计划和公开命令显式接收并绑定 parser 合同、locks、资源/材料身份及拟用途，计划审阅摘要包含这些输入；缺失或变更时拒绝，不默认接受任意目录或沿用仅限 U0_REHEARSAL 的准入。
- [ ] 默认 acquisition、staging 与 assembly 链实际纳入文档/图片 roots，固定来源和归档完整性；真实获取与提取结果核对完整集合，不能把未经可信过程验证的外部收据当作来源证明。
- [ ] 在 app 的最终确定性归档前注入完整资源，并核验重打包后的最终产物；精确准入包内容和链接，保留既有 external/Pi/PTY 行为，不通过放开全部依赖目录或改根安装来解决资源缺失。
- [ ] 合并 parser、external、Pi 及实际 native/非 npm 资产身份和来源，完整进入 acquisition ledger、两种 SBOM、notices 及必要版权/许可原文；最终文件和元数据逐项对账，同名同版本摘要冲突、未使用声明绑定、缺文本或遗漏资源均失败。
- [ ] 对当前最终包及具体拟分发场景核验适用条件和实际履行；所有当前必需义务有候选身份与证据，后续仅在安装/发行核对发生的证据明确交接 [G2-N05 / #28](https://github.com/Ricardo121380/only-my-pi/issues/28)，不提前记为完整许可或 Full 通过。
- [ ] 用当前候选实际执行默认准备/组装并从最终 app 包加载解析资源，证明无 checkout/全局回退；同时通过相关双 Node 合同/组件验证及漂移、缺输入、越界、符号链接、错误用途、摘要冲突和失败清理负例。注入 prepare 替身或注入前 pack 检查不能作为实际默认链出口。
- [ ] 使用精确可追溯的干净源码快照和新的仓库外输出，核对空间及输入身份，保留当前脏工作树；失败仅处理本次输出，长期证据不放入可能被清理的构建目录，用户原材料和日常栈保持。
- [ ] 交付当前最终包、完整元数据、实际命令/退出码、身份与 Standards/Spec 结果，F03/F04 满足后交给隔离 Full。规格允许的隔离设计和夹具准备可预先进行；这些准备不关闭本工单或放行 Full。
