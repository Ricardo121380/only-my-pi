## 核验后建议与采纳边界

以下是提出卡片时的工程建议；R1–R3 已确认 S0 修复优先、渐进整理和计划更新，具体实现仍须经测试证据验证，不能把建议本身当成修复完成。

1. 保留 React + OMP Host + Pi RPC → Electron 路线、Glacier 风格、对话优先布局，以及已确认的完整 WebUI 范围。
2. 新增安全与可靠性修复门槛，优先处理 E1–E6，并在规划中追踪 E8 的实际工具链验证。R1 已确认先完成 S0，再进入 U0。
3. 把 E7 加入现有 U0 预览技术验证和 U5 实现验收；原先“预览与 Agent 同时使用”的目标不降级。
4. 校准验证策略：纯文档和小修改仍做适度定向检查；代码实施前建立可复现基线，集成及候选晋级时有明确完整回归门槛；同一未变化候选的有效证据可复用。新发现失败必须追踪，不能用“不重复全量”跳过。
5. 报告中的全仓清理、删除所谓不可达包、全面迁移类型系统、升级 Pi、压缩历史门禁等分别论证；不与紧急缺陷捆绑自动执行。
6. 发布安全更新、远端备份/推送、磁盘清理及收费验收不因报告建议而获得授权；若后来需要，按具体操作边界处理。

补充约束：

- 当前 CI Node 矩阵为 `22.19.0`、`24.19.0`（`.github/workflows/ci.yml`），报告的本机 Node 26 测试不能替代支持矩阵。采用可用的隔离方式核验，不擅自替换全局运行时；环境不足如实保留未验证项。
- 完整自动化回归与真实付费模型、公开发布是不同边界。S0 不借用已耗尽额度，不默认收费或切换日常 active；拟以本地可控模型和隔离候选验证所需机制，不能冒称收费 Provider 验收。
- S0 出口只证明本批修复及受影响既有行为通过，不宣称 U0–U6 新功能完成。
- 预览尚未实现，其 cookie 泄漏/重放、源文件写入与服务生命周期的验证明确留在 U0-06 / G0-05，U5-04 / G5-04 再验；如果 S0 认证改动影响预览合同，应同步记录但不提前开发预览。
- Host 实现类型覆盖、前端状态及组件拆分按 R2 随实际改动渐进推进；采用最小可验证变更，不单列全仓重构。
- 一般工程细节由后续实施证据决定；新发现阻断若涉及新产品取舍、安全承诺或授权变化，报告具体差异再讨论，不自行扩充成无限整改。
