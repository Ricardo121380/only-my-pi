## 1. 最终目标

**Only my pi 同时交付直接基于最新稳定版 Pi 内核的 CLI/TUI 和桌面 Agent 客户端。图形端先完成可日常使用的 WebUI，再复用界面与必要的本机能力交付桌面客户端。**

这是用户在 2026-10-17 补充明确的最终形态：CLI 的产品形态类似 Claude Code，桌面的产品形态类似 Claude app 的 Code 模式。这些类比只表达使用方式，不推定其他产品的内部架构。CLI/TUI 与桌面都是正式产品入口，CLI 持续迭代并独立验收；WebUI 是图形端的先行交付形态。后续任务须说明它改善哪一端的哪个用户动作，或解决哪个必需的共享能力。

本轮进一步确认：完整已选 WebUI 验收后再进入桌面；同一项目的会话可双向查看和接续，同一会话同一时刻只由一端执行；CLI 可显式选择并使用产品账号，保留原账号归属且不自动切换；在不削减完整范围和最终门槛的前提下，按真实依赖先推进独立功能。跨项目并行、同项目单写与停止后接续的既有约定继续适用。

设计质询第一轮再确认：首个完整版本要求 CLI/图形端核心编程能力对等，相同账号、会话、工具和已选材料均可用于编程，整理/审查/预览采用适合各端的交互；新 Pi 暂不兼容时以已验收能力为先，明确版本差距并继续不受影响的工作；材料输入允许评估功能等价替代实现，保留全部已选格式、本机处理及安装验收，具体路线比较后再决定。

第二轮确认：CLI 独立完成产品账号新增/登录及 MCP、已选工具配置，认证需要时可打开服务商网页，无需启动 Only my pi 图形端。产品配置采用两端共用默认值加项目覆盖，原 Pi/用户外部配置保留归属且仅显式导入。首版接续只保证配套已验收运行组合；未验证组合只查看可读历史并提示匹配版本，不自动改变另一端安装。

Only my pi 是产品名称，不要求为这个名称建立一层 Agent 内核或中间服务。Pi 负责 Agent loop、模型调用、工具执行、上下文与会话历史；产品代码负责交互、项目组织、账号选择、审批交互及本机集成。已有需求优先使用 Pi 的公开 CLI、SDK 和扩展点实现，避免复制上游会话管理、工具调度或模型注册能力。

沿用 [ADR-0013](../decisions/ADR-0013-direct-terminal-coding-agent.md) 的直接终端入口和 [ADR-0014](../decisions/ADR-0014-webui-to-electron.md) 的 React WebUI → Electron 交付顺序。下图表达目标接入关系，不冻结进程数量，也不要求新增共享框架：

```text
Only my pi
├─ CLI / TUI ─────────────────── Pi CLI / SDK
└─ 图形界面（共享 React UI）
   ├─ WebUI ─── 本机 Node 进程 ── Pi SDK，或 Pi RPC 子进程
   └─ 桌面 ──── 应用内本机进程 ── Pi SDK，或 Pi RPC 子进程
```

普通浏览器需要本机进程来运行 Pi、访问项目文件和终端；这不要求该进程再维护一套 Agent 运行语义。桌面接入同样需要承载 Pi 的本机运行位置，但不预设必须照搬 WebUI 的常驻 HTTP 服务。CLI 不以 WebUI Host 为运行前置。

简化应先列清“Pi 已提供 / 产品确实需要 / 重复封装”，再在相同行为验证下删减。当前审批、项目写入协调、账号绑定及输入确认已有明确合同；改变接入方式必须证明这些行为仍成立。SDK 的 MCP/codemode 等内置扩展需要显式装配，也不能将更短的启动示例直接视为与现有产品等价。本次只修正目标与迭代约束，没有删除运行代码或决定最终进程拓扑。

首个桌面交付继续面向本机、单用户、中文、macOS Apple Silicon 自用安装包；现有 macOS/Linux CLI 继续作为正式终端产品交付。Linux GUI、Windows、远程团队、签名公证和公开发布仍是后续范围。CLI 的产品地位在本次明确，具体新功能仍须按用户动作定义，不凭产品类比扩张功能清单。

2026-10-18 Q11 已确认：新增产品账号、共享配置、材料输入与会话接续先在 **macOS Apple Silicon** 完成 CLI/图形端核心能力对等；Linux CLI 继续维护现有能力，新增能力随后独立适配和验收。Linux 新能力不是首个完整 macOS WebUI 或桌面出口的前置，既有 Linux CLI 的兼容和受影响回归仍须保持；这一顺序不代表 Linux 新能力已通过或永久取消。

## 3. “最新版 Pi”的工程含义

采用最新**稳定发布版**作为每轮升级目标，核对官方 Release 与 registry 后冻结精确版本、来源和完整性。2026-10-17 的下一目标是 **Pi 1.3.0**，预检时开发依赖为 **1.1.0**；后续 #76 已精确冻结 **1.3.0** 并验收，#77 的 `pi130-v1` 候选身份与当前结果见顶部报告。

一次升级按“上游变化核查 → 公开接口与必要封装核查 → 精确开发依赖/锁 → 新运行合同与候选 → 实际 CLI/Pi/WebUI 回归 → 安装验收”推进。开发 pin、已安装依赖、候选栈、日常栈和对外发布版本分别报告。

每轮开工及候选冻结前检查一次上游；冻结后的验证绑定同一候选。中途的新版本进入下一次有界升级，安全修复或明确阻断可触发重新冻结和受影响复验。交付时声明精确版本及检查日期；落后于当时上游时明确差距，不把旧候选称作最新版。此流程是执行约定，没有创建后台监控或自动更新器。

Q6 已确认以已验收能力为先：新版暂时破坏授权、会话或工具等必要能力时，保留最近已验收的候选，记录版本差距、失败原因与适配任务，继续经核对不受影响的功能。新版兼容通过后再升级，不因追逐版本号删除必要能力，也不把新版适配设为所有独立工作的永久前置。

Q10 将首版跨端接续承诺限定为配套已验收运行组合：记录两个客户端及其 Pi/扩展、配置和历史合同身份，不能只比较 Pi 版本字符串。未验证组合对共享会话只展示可读历史，提示所需匹配版本；不自动接续、迁移其不理解的数据或更改另一端安装。历史不可读时保留原件并明确说明；旧 CLI 自身既有能力仍按其原支持范围判断。

升级保持账号、历史、输入账本、权限和单写协调；新上游功能只在已选范围内启用。旧合同、原候选和失败记录保留。Pi 1.3.0 的重试及恢复工具行为须实际核验，不能让升级带来未经同意的额外请求或授权恢复。

### 首个完整版本的使用流程

1. 安装/启动 CLI 或 WebUI，独立完成产品账号新增/登录及必要工具设置，明确选择项目、账号与模型；配置缺失或失效有具体原因。
2. 理解项目、讨论计划、批准编程，看到真实工具、子任务、补充/队列和取消状态。
3. 加入所选文件、图片或现代文档；实际发送内容与卡片、快照和历史一致。
4. 查看改动和验证结果，必要时交给人工编辑/终端，再交回 Agent；用户已有修改不被覆盖或错误归因。
5. 查看可追溯的用量、资源配置及并行预览；失败、断线和未知结果可以定位并保守恢复。
6. 停止会话，在配套版本的另一端选择同一项目/会话继续；核对账号并重新取得执行授权，旧历史与产物可读。未验证版本组合只查看可读历史并提示匹配版本。
7. 安装升级、回滚并重新应用同一候选，保留合法新增数据。桌面阶段对这套流程再做实际安装包验收。

## 7. 后续每轮如何执行

1. **选定一个可完成的用户动作。** 写清问题、用户结果、范围、现有 Issue/Task/Gate、真正前置和不涉及的相邻功能。主代理同时只推进一个实施切片；子代理仅做有界探索或独立核验。
2. **冻结开工条件。** 核对 HEAD、已有修改、目标 Pi/Node/候选、接口、历史数据影响和必要环境。已知失败保留；无未解释的必需失败才进入依赖步骤。
3. **沿完整链路实现。** 接口、持久化、运行适配和界面共同交付一个可操作结果；优先复用当前模块，局部整理随功能发生。避免只交付按钮或只交付后端字段。
4. **验证到实际边界。** 变更有定向回归；CLI 使用实际 CLI/PTY→Pi→本地受控服务，图形端使用实际 Pi 接入与 Ego Lite；候选整合再跑适用完整清单。同一未变候选已有效的证据可复用，新版本及新增范围必须补证。
5. **审查并收口。** 分别检查仓库标准与规格完成条件，解决阻断后记录归属增量、命令/退出码、候选和证据。代码完成先标待验收；必需层次全部通过才关闭任务。
6. **更新当前入口再进入下一项。** 给出用户可见变化、验证层次、具体阻断及下一项。阶段门槛满足且授权仍覆盖时自主继续；收费服务、日常安装切换和远程发布按具体对象与既有授权判断。

任务状态使用待开始/开发中/待验收/已验收/阻断；证据使用 PASS/FAIL/PARTIAL/BLOCKED/NOT_RUN/UNKNOWN。C、P、B、I、L 的含义沿用[验收矩阵](2026-09-26-webui-optimization-acceptance.md)。只读静态核查不是 C/P/B 运行通过，受控服务不是实际 Provider，未执行不计为失败或成功。

以“可操作用户旅程、阻断数量及原因、迭代交付”观察进展。原 20/44、关闭 Issue 数和测试数各自保留语义，不合成虚假的总完成率。没有可靠工时和容量依据时不承诺人周或上线日期。

每个实施切片的开工条件是：用户结果明确、关联需求/工单与真实前置齐全、数据兼容影响已知、可用验证环境和本轮修改归属已冻结。完成条件是：实际入口具备结果，成功/拒绝/失败/取消等相关路径通过，源码与候选证据对应，文档已同步，必需失败已处理。只完成类型、按钮或帮助函数不能关闭用户功能。

回归按影响范围执行；整批候选完成适用完整清单。复用已有性能目标：固定样本输入 P95 < 100 ms、本地取消确认 P95 < 500 ms、热索引检索 P95 < 500 ms、预览可见更新 P95 < 2 秒，样本/硬件和实际进程退出分别记录；不把目标值写成已测结果。材料/Full/真实服务/日常晋升各自保留出口，详见[验收矩阵](2026-09-26-webui-optimization-acceptance.md)。

主代理负责方案、实现和最终验证；子代理只做聚焦探索与独立核验。每轮交付列出用户可见变化、归属 diff、实际验证、仍阻断内容及下一可开工项。避免为流程本身增加无用户结果的批次。
