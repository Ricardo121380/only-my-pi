## 1. 已确认的目标与交付边界

采用 **React + OMP Host + Pi RPC → Electron**，保留现有 Pi/OMP 内核、CLI/TUI 和受控编程流程。先交付可日常使用的本机 WebUI，再交付 macOS Apple Silicon 自用桌面安装包。

| 领域 | 确定方案 |
| --- | --- |
| 使用范围 | 本机、单用户、先自用；公开预览后续安排 |
| 界面 | 中文三栏工作台：项目与会话、对话与执行、文件与审查 |
| 编辑能力 | 文件树、多标签、语法高亮、搜索、保存、diff；首版不做语言服务器和调试器 |
| 人工终端 | 内置交互终端；终端存活期间独占该项目写入 |
| 并行 | 跨项目并行，同项目单写；人工操作、GUI Agent、CLI 共同遵守写入所有权 |
| 会话 | 与 CLI 共享历史，只续接已停止会话；续接不恢复编程授权 |
| 后台执行 | 页面关闭或刷新后，已授权任务继续；新审批等待重连；退出 Host 取消执行，重启后授权失效 |
| 账号 | GUI 支持同 Provider 多账号、API Key、自定义 Provider 和 Pi 已支持的 OAuth；每会话显式绑定账号 |
| 账号切换 | 当前任务停止后才能切换；失败或额度不足不自动换账号；CLI 保持原默认配置 |
| 开发方式 | 用户负责产品方向，Codex 实施；无硬上线日期，阶段门禁通过后自动继续 |
| 设计辅助 | 优先使用 Open Design 中的 K3；不可用时说明情况，由当前 Codex 继续 |
| 验收 | 自动化检查、浏览器操作和有界真实模型测试；每阶段最多 3 个小型真实任务及 1 次失败重试 |

保留现有 Linux CLI 支持。Linux GUI、Windows、英文界面、远程访问、团队协作、插件市场、签名公证和公开发布不计入这三阶段。英文按照讨论结果在后续公开预览前补齐。

## 2. 架构、接口与行为合同

### 2.1 组件职责

| 组件 | 职责 |
| --- | --- |
| 共享 React WebUI | 项目、会话、执行流、审批、账号管理、编辑器、终端和差异审查 |
| OMP Host | 本机连接、项目与会话目录、worker 生命周期、任务队列、事件投影、账号管理、文件与终端接口 |
| OMP RPC worker | 在独立进程中加载审核过的 Pi/OMP 运行核心，执行任务并落实最终授权判断 |
| Pi | Agent loop、模型调用、会话历史及正式 RPC 协议 |
| Electron | 承载共享 WebUI，提供窗口、菜单、目录选择、通知和安装分发 |
| 共享协调模块 | CLI、Host 与 worker 的项目写入所有权、会话占用和运行身份检查 |

新增前端使用 TypeScript、React、Vite；基础编辑器采用 Monaco，终端采用 xterm.js，PTY 在 Host 的 Node 进程中运行。延续现有 npm 工具链；依赖采用实施时验证过的精确版本并锁定。

Agent 执行继续采用 Pi 正式 stdio RPC。账号管理使用同版本的公开 `ModelRuntime`；必要的 worker 启动注入使用公开服务创建接口和 `runRpcMode()`，不依赖实验性 Pi server/client，也不导入私有 `AuthStorage`。[Pi RPC](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/rpc.md)、[公开入口](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/src/index.ts)

### 2.2 对外入口与最小接口

新增 `omp web` 启动或连接本机 Host，并打开浏览器；保留 `omp -- "web"` 作为普通任务文本的消歧方式。增加 Host 状态与显式退出命令，桌面端提供同等操作。

Host 对外提供以下能力组：

- **项目与会话**：登记项目、列出历史、创建会话、续接停止的会话、查询执行状态。
- **任务与审批**：开始任务、取消、撤权、响应审批、读取快照、订阅后续事件。
- **账号与模型**：账号目录、登录/登出、Provider 配置、模型选择、会话账号绑定。
- **文件与审查**：受限文件树、读取、条件保存、差异与验证回执。
- **人工终端**：创建、输入、调整尺寸、重连和关闭。

浏览器使用本机 HTTP/WebSocket；Pi 原始 RPC 不直接暴露给浏览器。接口只返回必要的、脱敏的产品数据。

同一 GUI 数据目录只运行一个兼容 Host。不兼容版本拒绝连接，避免桌面与浏览器悄悄启动两套管理进程。

### 2.3 必须保持的运行规则

**授权与写入所有权分别管理。** 编程授权决定允许做什么；项目写入所有权决定当前由谁执行。原有 `omp -p` 和普通 headless RPC 保持只读，GUI 使用新增的受控交互宿主入口。

以规范化项目路径协调所有写入口，包括主 Agent、受管补丁应用、真实工作区检查、编辑器保存和人工终端。会话历史另设占用检查，防止两个进程同时续接同一历史。

人工编辑在显式“手动模式”下保存；离开该模式先处理未保存内容。人工终端存活时保持项目所有权，关闭终端及其子进程后才能交还 Agent。页面断开不释放仍在工作的进程所有权。

Host 存活时，已授权任务可以继续执行。新审批保持等待；过期、已取消或被替代的审批答复不能重新授予权限。Host 退出时取消任务、关闭 PTY 并使待审批失效。Host 崩溃后的遗留进程必须核实，不能仅凭超时抢占其项目。

### 2.4 多账号与配置隔离

OMP 管理独立 `accountId`，Pi 的真实 `providerId` 保持不变。每个 GUI 账号使用独立凭据存储和模型缓存，会话只记录非秘密账号绑定。

worker 启动时注入账号对应的 `ModelRuntime`，同时保留受控资源与共同会话历史。这样可以隔离账号，而不因修改整个 Pi 配置根导致安全扩展、信任和历史意外分裂。[ModelRuntime 配置接口](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/src/core/model-runtime.ts)、[服务注入接口](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/src/core/agent-session-services.ts)

具体规则：

- CLI 原默认账号作为只读管理引用使用；GUI 登录、换 Key、登出操作针对 GUI 自有账号。
- 不复制正在刷新的 OAuth token，不把密钥放入模型提示、启动参数、浏览器持久存储或日志。
- 账号缺失、删除或不可用时要求显式选择，禁止回退到其他账号或环境中的隐含凭据。
- 账号切换、配置删除和登出须在受影响任务停止后进行；重新启动 worker，重新验证授权。
- OAuth 按 Pi 的认证能力动态呈现；首版串行处理登录流程，避免固定回调端口冲突。
- 自定义 Provider 表单只支持明确的静态配置，不新增执行任意配置命令的入口。
- 区分“凭据已保存但刷新失败”与“登录失败”，避免重复登录覆盖状态。

### 2.5 持久化与重连

Pi 继续作为聊天历史的权威来源；OMP 保存自身项目索引、账号绑定、控制状态及运行回执。首版沿用本地文件与原子写入方式，不新增数据库服务。

重连先获取快照，再接收有序事件。文本增量可以合并，审批和执行终态不能丢失。写入命令必须去重，断线后不得自动重放补丁应用。

界面分别显示：

- 任务执行状态；
- 补丁是否已应用；
- 目标工作区是否验证通过。

`APPLICATION_UNKNOWN` 必须保留为待核对状态，不能显示成失败未写入或自动重试。

## 3. 三阶段开发顺序与退出条件

### 第一阶段：固化基线，建立 Host 与只读 WebUI

沿用当前目录形成核对过的本地源码基线；WebUI 汇总当前生效 Pi 会话根中的全部历史项目，旧历史只读，新建会话执行只读分析，并提供文件预览、Git diff 和回执。候选通过后升级日常 CLI；具体任务、接口和证据要求见[第一阶段详细计划](2026-09-20-omp-webui-phase1-plan.md)。

| 批次 | 实施内容 | 批次验收 |
| --- | --- | --- |
| **1A：基线收口** | 记录当前 HEAD、既有未提交修改与测试基线；复核现有安全修复；统一源码、OMP、Pi、Node、扩展和协议版本信息 | 保留已有用户内容；明确发布基线、未发布修复与新增目标；关键安全测试没有未解释失败 |
| **1B：Pi 升级** | 构建真实 0.85.1 候选；新旧运行合同并存，外部扩展使用栈内受控副本，保留补丁、信任、预算与旧栈回滚能力 | 实际候选身份与完整扩展/补丁通过，隔离安装回滚成功；用户原包保持不变 |
| **1C：Host/worker 骨架** | 建立本机启动、连接认证、项目/会话目录、只读 RPC、事件快照、进程生命周期与协调模块 | 未授权连接被拒；只读接口不能取得写权限；重连不重复执行 |
| **1D：高风险技术验证** | 在专用临时 Git 项目中，以模拟模型验证真实工具写入、撤权、取消、账号注入与跨进程协调；普通 UI 保持只读 | 真实进程与工具边界通过，同 Provider 两账号隔离成立 |
| **1E：只读界面与设计合同** | 完成中文三栏、全部 Pi 历史项目索引、对话/工具输出、新建只读分析、文件/diff/回执 | 构建、组件和 ego-browser 检查通过；完成 M1-T 所需候选验收 |
| **1F：日常安装晋升** | M1-T 后执行日常 Full 栈切换、回到升级前 active、重新应用同一候选及最终 smoke | PATH 中真实 OMP 身份正确；用户数据与原扩展保留；M1-I 通过 |

**M1 退出条件：M1-T 与 M1-I 均通过。** M1-T 证明候选运行核心、Host、只读 UI、账号/授权探针与候选验收成立；M1-I 证明日常安装切换、显式回滚、同一候选重新应用及安装态真实任务完成。仅候选通过不算第一阶段完成。

若升级或受控 RPC 验证失败，停在该门禁修复；回滚成功不能替代升级验收通过，也不能通过削弱权限检查继续推进。日常切换时存在用户活动会话则保持待切换，不强停；凭据与历史不被旧快照覆盖。

### 第二阶段：交付可日用 WebUI

| 批次 | 实施内容 | 批次验收 |
| --- | --- | --- |

| **2F：整合与性能** | 统一导航、账号/模型状态、排队提示、异常恢复、长会话渲染和大输出处理 | 约定端到端矩阵、视觉检查、性能样本与真实模型验收通过 |

**M2 退出条件：** 能在同一个 WebUI 中完成账号配置、项目选择、编程任务、手动编辑、终端操作和结果验证；关键异常能够解释并恢复，不靠修改内部文件处理正常流程。

模型失败不会触发静默换账号；补丁应用结果未知不会触发自动重试。

## 4. 验收矩阵与自动推进规则

### 4.1 必测场景

| 验收组 | 核心场景 |
| --- | --- |
| 基线兼容 | CLI 启动/退出、会话恢复、只读限制、授权撤销、预算、受管 writer 和项目检查 |
| 授权 | 拒绝、取消、迟到答复、重复答复、切换会话、Host 重启、页面断开待审批 |
| 写入协调 | CLI 与 GUI 竞争、两个窗口、符号链接别名、人工终端占用、进程崩溃、失效所有者 |
| 账号 | 同 Provider 两账号、OAuth 刷新并发、切换与登出、环境凭据回退、账号删除、存储成功但同步失败 |
| 会话 | 只续接停止会话、共享历史不分裂、恢复不恢复授权、账号绑定缺失时不自动选取 |
| 文件与终端 | 外部编辑冲突、越界路径、中文输入法、PTY 重连、后台子进程、退出后的进程清理 |
| 运行结果 | 克隆通过但真实验证失败、应用期间取消、应用结果未知、回执和补丁身份不匹配 |
| 本机服务 | 未授权请求、异常 Origin/Host、跨站请求、无效协议版本、连接背压与超限输出 |
| 桌面安装 | 干净环境、无系统 Node、版本不兼容、升级中断、回滚、CLI/桌面同时存在 |

OAuth 的协议与界面分支通过模拟服务覆盖；真实 Provider 只对本次实际走过的流程作互操作声明，不声称所有 Provider 都完成真人登录验收。

前端操作测试使用 **ego-browser**。若该工具不可用，相关验收记为未完成，不静默换用其他浏览器测试工具。

现有验证脚本按受影响范围复用。`verify:m12` 的展示结果不等于 `verify:m12:run` 的执行结果；历史 C11/C12、安装证据及调研时的定向测试不能直接给新增 Host/GUI 标记 PASS。基线已有失败与新增失败分开记录，必需安全门禁失败不能作为已知问题豁免。

### 4.2 性能与体验验收

固定验收机和样本，至少包含 10,000 条事件、5MB 工具输出和长 diff。

- 本地输入回显 P95 目标低于 100ms。
- 取消请求本地确认 P95 目标低于 500ms；子进程实际退出另行记录。
- 长会话采用虚拟化或分页，渲染过程中不得持续阻塞输入。
- 记录整个进程树内存、冷启动、包体与更新体积，区分新增功能成本与异常增长。

以上是验收目标，不是现有 OMP 已达到的测量结果。本地取消确认也不等于远端模型已经停止计费。

K3 辅助产物需落实为布局、组件状态和交互规则，并通过实际页面检查。视觉验收不能仅凭生成截图通过。使用 Open Design 前核实精确 K3 模型与路由；不可用时按照用户已选的后备方式说明并由当前 Codex 继续。

### 4.3 真实模型验收

只复用现有已配置路由，不开通新服务。每阶段最多 **3 个小型任务＋1 次失败重试**，使用隔离临时项目：

- 第一阶段：两个候选 WebUI 只读任务覆盖分析/流式与取消，一个最终安装态 CLI 小型修改与检查任务；前三者合计仍受 3 个任务＋1 次失败重试上限约束。安装回滚本身使用无模型检查。
- 第二阶段：小型修改与验证、受管写入、撤权/取消。
- 第三阶段：安装包内重跑核心闭环与恢复场景。

上述限额是整个阶段累计限额，不是每个批次重新获得一份额度。记录实际路由、任务、调用结果及可获得的用量。额度、认证或网络导致未完成时明确记为 `NOT_RUN` 或失败，不把模拟结果充作真实验收。

### 4.4 自动推进

每个批次执行“实现 → 定向测试 → 差异审查 → 修复 → 证据记录”；阶段末执行整合门禁。**全部必需门禁通过后自动进入下一阶段，不重复请求阶段批准。**

证据至少包含源码与工作树身份、运行核心版本、测试结果、界面截图、真实任务结果和遗留问题。使用 PASS、FAIL、NOT_RUN 等明确状态；未完成项不能填入通过状态。

阶段自动推进不取消 OMP 产品内的编程审批，也不扩大验收任务的项目范围、模型路由或外部发布权限。

遇到以下情况停止依赖该问题的后续批次，继续可独立工作：

- 授权、账号隔离或写入所有权存在未解决失败；
- 必需环境或真实验收无法完成；
- 完成任务需要扩大已确认范围、新服务或新的外部发布行为。
